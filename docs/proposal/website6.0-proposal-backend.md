# website6.0 后端方案：AI 能力集成方式评估 + 密钥安全与配额结论（方案阶段，不出码）

作者：后端 ｜ 日期：2026-10-23 ｜ 状态：待项目汇总、站主确认
输入依据：shared/website6.0-requirements.md、shared/website6.0-proposal-frontend.md（落点①构建期 AI 新闻管线、落点④BYOK 兜底）、shared/website6.0-proposal-product.md（P0/P1 清单）、shared/website6.0-proposal-devops.md（仓库公开、Pages+Actions 通路）
前提：GitHub Pages 纯静态（无运行时服务端）、公开仓库、无 serverless。本方案回答前端移交的三个问题，并给出站主裁定项。

---

## 0. 结论速览（供项目直接引用）

1. **落点①放 GitHub Actions（公开仓库）调 LLM API：安全合规，推荐必选**。前提是遵守 §1.2 的 4 条 workflow 红线；配额靠"固定批次 + 节流 + 失败兜底 + 用量告警"四层控制（§1.3）。
2. **BYOK（落点④）：有条件启用——启用但默认关闭、入口收敛在 AI 问答设置区内，属 P1 实验特性，不是上线阻塞项**。风险边界与 5 条硬约束见 §2。若站主顾虑安全争议，砍掉它不影响任何 P0 需求。
3. **不需要 serverless/外部服务**。静态 + Actions + 浏览器 API 已覆盖全部 P0/P1 AI 需求（逐条盘点见 §3）。"共享密钥运行时代理"这一唯一需要 serverless 的场景，被本阶段"零运行时密钥"策略主动排除；保留未来引入 Cloudflare Workers 的决策出口与否决理由（§3.3）。

总推荐架构：**一个密钥、两个消费面**——站主自持 1 个 LLM API key，只存在于 Actions Secrets（CI 端）和访客浏览器 localStorage（BYOK 端）两个位置；站点服务端不存在、不上传、不代理。

## 1. 落点①：GitHub Actions 构建期 AI 新闻管线——安全合规性与配额

### 1.1 安全性判断（公开仓库 + Actions Secrets）

结论：**安全**。依据：

- Secrets 以加密形式存储于仓库设置，仅对仓库自己运行的 workflow 可见；不进代码库、不进构建产物、不在日志中明文回显（GitHub 对 `::add-mask::` 自动脱敏）。公开仓库暴露的是工作流定义与产物，不是密钥本身。
- 定时（`schedule`）与 `push` 触发的 workflow 天然运行在受信上下文，可安全使用 Secrets。公开仓库 Linux runner 与 Actions 用量免费，schedule 任务可长期跑。
- 合规性：密钥为站主账号自持自用，不涉及密钥分发或转售，符合主流 LLM 提供商 ToS；"抓取 RSS 正文 → LLM 生成中文摘要/标签 → 发布标题+简介+原文链接"属于常见的摘要引用场景，需在新闻条目保留来源出处（方案本身即直跳原文，满足）。
- 唯一真实风险面是 **密钥被 workflow 逻辑泄露**，靠 §1.2 红线规避。

### 1.2 Workflow 安全红线（写入验收标准，测试可 grep/审查验证）

1. **禁止**任何读取外部（fork PR）代码并与 Secrets 同 job 执行的组合，尤其禁止 `pull_request_target` + checkout PR ref 的写法。个人站无外部贡献者场景，新闻管线 workflow 仅 `schedule` + `workflow_dispatch` 两种触发，从源头消除该类攻击面。
2. Secrets 仅注入新闻管线这一个 job，通过 `${{ secrets.LLM_API_KEY }}` 环境变量传递；不得把密钥值写入任何 commit、artifact、issue/PR 正文或 `$GITHUB_STEP_SUMMARY`。
3. 产物兜底检查：pipeline 末段加一步"密钥痕迹扫描"（对 `news.json` 与 dist 产物 grep 密钥前缀特征，命中即 fail），与产品验收标准"密钥不得出现在构建产物"是同一条门禁的两个方向。
4. `GITHUB_TOKEN` / 用于提交 `news.json` 回仓库的凭据一律最小权限（仅 `contents: write`），且与 LLM 密钥互相独立、不可互换。

### 1.3 配额与成本控制（四层，从源头到预警）

前提假设：每日 2 次 schedule；单次 LLM 调用输入为截断后的正文（每条 ≤2k token 量级），输出为短摘要+标签。具体数字在实施期按所选提供商官网口径校准，这里定**机制**不定**数额**。

| 层 | 控制手段 | 说明 |
|---|---|---|
| 1. 调用量封顶 | 每次 run 固定批次上限：每源取 top N（建议 ≤40 条）、单次 run 摘要调用 ≤100、全 run 目标 ≤150 次调用 | 白名单源 × 2 次/日 × 100 条 ≈ 每日 ≤400 次调用，属免费档可承载量级 |
| 2. 节流 | batch 内串行 + 步间 sleep，遵守提供商 RPM（每分钟请求）限制；失败重试 ≤1 次，不写无限重试 | 防止 429 风暴，防止异常循环烧配额 |
| 3. 幂等与去重 | 已收录条目 URL 指纹去重，二次 run 只处理增量；全量失败时沿用上一版 `news.json`（提交回仓库保历史，兼得知识侧"AI 周报档案"素材） | 把"配额事故"的自然上限压到增量规模 |
| 4. 用量告警 | 站主在提供商控制台设 usage alert / 硬限额（人工操作清单新增一步，约 3 分钟） | 唯一能在提供商侧真正"熔断"的手段，CI 内做不了跨 run 花费上限 |

**提供商选择建议**（站主裁定项，见 §4 B-1）：首选有免费档、免信用卡起步的端点（如 Google Gemini API 免费档；备选 OpenAI 兼容或 DeepSeek 低价档）。选择标准三条：① 免费 RPM/RPD 能承载 ≤400 调用/日；② API 无强制信用卡（降低站主绑定支付的心理与操作成本）；③ 与前端 §落点④ BYOK 用同一提供商，访客侧与 CI 侧代码路径统一。

### 1.4 剩余风险（明确告知，不隐藏）

- Actions schedule 在高峰期可能延迟触发（GitHub 已知行为），新闻更新时效 ±小时级波动——对个人新闻站可接受。
- 提供商免费档政策随时可能调整（额度缩小/收费），属于外部依赖风险；缓解：管线输入源列表、prompt、产物 schema 与提供商解耦，换 key/换提供商只改 Secrets 与一个适配层。
- `news.json` 提交回 main 需要 workflow 写权限；若站主不希望 bot 直接 push，可改为产物入库由人每周批量合入（牺牲自动化程度换更严格的人工审计，列入裁定）。

## 2. BYOK 方案（落点④：访客自持 key + localStorage）——风险边界与产品建议

### 2.1 技术可行性确认

- CORS：Gemini API 与 OpenAI 均支持浏览器携带 API key 直连（官方文档明确提供 `x-goog-api-key` query/header 的浏览器用法），无需代理。✅ 静态站成立。
- 密钥位置：localStorage 明文。这是 BYOK 模式的固有属性，无法通过前端手段变成"安全存储"，只能收窄暴露面（见 2.2）。

### 2.2 风险边界（按威胁源枚举）

| 威胁 | 现实风险 | 边界/缓解（必须全部满足才允许启用） |
|---|---|---|
| 站点 XSS 读取 localStorage | 中低（站内容为构建期受控产物 + 有限 MDX） | 站点部署 CSP（meta 标签级，Pages 不支持自定义 HTTP 响应头是已知限制，见下注）、AI 模块不在页面脚本中读 key、仅在用户显式点击"开始问答"的调用栈内读取一次 |
| 恶意浏览器扩展/用户被诱导粘贴脚本 | 存在，但已超出网站责任边界 | 使用前显式知情提示 + key 输入框为 `type=password` 语义 + 一键清除 + 会话级"清除我的数据"入口 |
| key 被站点上传/记录 | **必须为零** | 硬约束：fetch 目标域名白名单仅提供商官方端点；日志/埋点/第三方分析一律不得接触请求头；此条进测试用例（网络层断言） |
| 访客误以为站点在收费/索取 key | 产品信任风险 | 文案明示"密钥只留在你的浏览器，本站无服务端、无法读取"；入口藏于 AI 问答"引擎选择"内，非首屏 |
| 提供商 ToS（key 属访客本人） | 无合规问题 | 消费主体即 key 所有者，站点仅是界面；不缓存、不转发、不代付 |

注（Pages 平台限制，需写进实施期验收）：GitHub Pages 不能下发 `Content-Security-Policy` / `X-Frame-Options` 等 HTTP 响应头（`_headers` 是 Netlify/Workers 特性）。可用 `<meta http-equiv="Content-Security-Policy">` 替代，但 meta 版不支持 `frame-ancestors`。本站无登录态无敏感服务端，点击劫持影响面小；BYOK 场景真正的防线是"key 只在用户手势调用栈内可读"的应用层约束，不依赖 CSP 单点。

### 2.3 产品建议：**启用，默认关闭，P1 实验特性**

理由：
1. 它是前端落点③（本地 RAG 问答）引擎梯度 `Built-in AI → WebLLM(opt-in) → BYOK` 的最后一档兜底；砍掉后"问站长"在 Unsupported 浏览器上退化为纯检索无生成，体验断尾。
2. 满足"访客用得起的高级用户"长尾，代码量小（一个 provider 适配 + 存储管理），与落点①共用提供商 SDK，边际成本低。
3. 但它**不符合 P0 的"零风险上线"定义**：涉及密钥 UI、localStorage、用户知情文案，测试面大。放 P1 与 ⌘K、View Transitions 同批迭代，不阻塞首发。

建议的启用门禁（写进站主裁定与验收标准）：
- 默认关闭；入口仅存在于 AI 问答面板的"高级设置"。
- 首次使用强制展示一段知情文案（key 去向、如何清除、费用归自己）。
- 提供"清除所有本地数据"按钮，且清除逻辑可测试。
- 网络层测试用例断言：除提供商官方域名外无任何请求携带 key。
- 站主若对"个人站提供密钥输入 UI"有洁癖，**整块砍掉不影响任何硬性需求**——这是它与落点①的本质区别（①是需求 5b 的实现路径，④是锦上添花）。

## 3. Serverless/外部服务需求判定

### 3.1 P0/P1 全量 AI 及相关需求覆盖盘点

| 需求/落点 | 优先级 | 实现载体 | 是否需要运行时服务端 |
|---|---|---|---|
| 业内新闻（标题+简介+直跳） | P0 | Actions 定时管线 + 静态 `news.json`（§1） | ❌ |
| Chrome Built-in AI 就地总结/翻译 | P0/P1 | 浏览器 API | ❌ |
| 本地 RAG"问站长" | P1 | 构建期 embedding（Actions 内用同一 LLM key）+ 端侧检索/生成 | ❌ |
| BYOK 云端兜底 | P1 | 浏览器直连（§2），CORS 已确认成立 | ❌ |
| AI 个性化（新闻排序/主题） | P1 | 端侧分类 API | ❌ |
| ⌘K 全站搜索/导航 | P1 | Pagefind 静态索引（website5.0 已验证的资产） | ❌ |
| 新闻 AI 周报档案 | P2 | `news.json` 历史 commit 即档案 | ❌ |
| llms.txt / JSON 端点（知识侧点子） | P2 | 构建期生成静态文件 | ❌ |

**结论：静态 + Actions + 浏览器 API 覆盖全部 P0/P1，无场景必须 serverless。**

### 3.2 盘点中被排除的"外部服务"候选及处置

- **联系表单**：需求未要求；以 `mailto:` + 社交链接规避。若未来要做，再评估 Formspree/GitHub Issues 表单（属外部服务但非 AI，不在本方案范围）。
- **共享密钥的运行时公共 AI 入口**（访客不配 key 也能用站主额度问答）：技术上唯一真正需要 serverless 代理的场景（前端不可持有 key、需服务端限流与防盗用）。本阶段**明确不做**——它同时引入密钥服务端化、配额盗刷、付费责任三类风险，与"零运行时密钥"策略冲突。若站主未来裁定要做，走 §3.3 出口。
- **统计/评论**：非 AI 需求，隐私友好型计数可后置（GoatCounter 类），评论不做。
- **WebLLM 模型权重**：走 CDN（huggingface/jsdelivr）按需拉取，属公共静态资源，不是服务端依赖。✅

### 3.3 保留出口（ADR 形状记录否决，供实施期复用）

决策：本期不引入 serverless 代理。触发重审的条件：① 站主希望"公共 AI 问答无需 BYOK"；② Actions 免费额度政策变化导致构建期管线不可持续的用量成本。届时首选方案为 Cloudflare Workers 免费档（10 万请求/日）做薄代理：key 存 worker 环境变量、按 IP/UA 限流、只代理摘要类小 prompt；代价是新增一个部署面与账号，需与"发布通路只走 GitHub"的简单性做权衡。理由与条件归档进 website6.0-decisions.md（呼应知识侧沉淀建议）。

## 5. 后端红线汇总（进全局验收标准）

1. 任何密钥只允许出现在两个位置：Actions Secrets、访客自己浏览器的 localStorage。仓库代码、构建产物、dist、commit 历史、issue/PR 中零密钥（grep 门禁，与产品验收标准合并为同一条）。
2. 新闻管线 workflow 仅 `schedule`/`workflow_dispatch` 触发；出现 `pull_request_target` 一律 review 拒绝。
3. BYOK 模式下站点侧对 key 零上传、零日志、零第三方共享；网络层测试断言通过才允许该特性发布。
4. 所有 AI 能力失效时（key 配额耗尽、API 故障、浏览器不支持），站内核心内容 100% 可用且新闻页自动回落到上一版 `news.json`。

## 6. 头脑风暴功能点子（后端视角，2 条）

1. **管线可观测面板**：把每日新闻管线的 run 状态、调用量、去重率、失败回落次数写成静态 `news-stats.json`，在 News 页脚放一个"本站数据心跳"折叠区——用真实运维指标自证工程能力（与产品侧"展示真实指标"点子同源，但秀的是 CI/数据面而非前端性能面）。
2. **LLM 防盗用蜜罐检测**：在 BYOK/代理出口预留一层"异常调用模式"检测思路（同一访客 key 短时高频、非常规 UA），本质是把 API 服务的 abuse 设计习惯带进静态站，作为 blog 素材写"个人站如何不烧钱地接 LLM"。

## 7. 假设与未知

- 假设站主愿意提供 1 个自持 LLM key（金额级预计每日调用在免费档内，月成本趋近 0）；若站主完全不想提供 key，落点①退化为纯 RSS 聚合无 AI 摘要（标题+简介仍可硬达标），此分支需在总方案中标注。
- 各提供商免费档具体额度数字（RPM/RPD/TPM）随政策变化，本方案只定控制机制，实施期第一步即以选定提供商官方页校准。
- Actions schedule 延迟、Pages 无自定义响应头为平台已知限制，非阻塞，均已给替代路径。
