## 二、website6.0 方案缺口与风险清单（本次分派未覆盖、需在汇总时补足）

1. **内容来源与更新机制未定义**：「业内新闻」只说了展示形态，未定数据来源——人工录入 content collection？RSS 聚合构建期抓取？AI 辅助摘要生成（涉及版权与准确性风险）？这是产品+前端+后端三方都要对齐的最大开口。
2. **"弱化简历入口"的验收标准未量化**：弱化到什么程度（不出现在主导航？仅在页脚？二级页面？）需要产品给出可验收定义，否则设计与测试无法判定通过。
3. **"最前沿技术"的边界未定义**：建议明确为可验收清单（如 View Transitions、Container Queries、CSS @scope、Web Components、Islands 交互、AI SDK 浏览器端调用等），并区分"必须用到"与"可选加分"，防止选型无限膨胀。
4. **AI 功能的成本与密钥风险是硬约束级问题**：GitHub Pages 纯静态 + 前端直连第三方 API 必然暴露密钥。后端的评估结论必须进方案正文，作为站主裁定项，不能只停留在技术附录。
5. **jary8.com 域名主权与 DNS 现状未盘点**：开发运维需确认域名注册方、当前 DNS 托管方与 5.0 的占用关系（6.0 上线 = 域名接管，存在新旧切换窗口风险）。
6. **无障碍与对比度基线**：5.0 已建立测试项（对比度/无障碍），6.0 换视觉方向后须重新过一遍，建议作为验收标准固定条目。
7. **数据与内容迁移策略**：需求说"可不参考 5.0"，但 5.0 上已有文章/项目的 SEO 资产（外链、收录）是否保留/重定向，需站主拍板，属待裁定项。
8. **旧站下线窗口**：域名切换后 website5.0 的去留（保留原仓库？归档？），知识库需要提前留档。

## 四、头脑风暴功能点子（3 条）

1. **AI 生成的"站内技能图谱"页面**：站长技术栈以交互式知识图谱呈现（点击节点展开相关项目/文章），内容由构建期 AI 从 content collection 聚类生成，纯静态可交付，同时直观"体现站长技术"。
2. **新闻聚合的"AI 周报"档**：业内新闻按周由 AI 生成一段 3 行综述存档（生成动作在构建期/本地完成，不落运行时密钥），既满足"标题+简介+直跳"，又形成可沉淀的档案价值，搜索索引也因此有料。
3. **面向 LLM/Agent 的站点接口**：提供 llms.txt + 结构化 JSON 内容端点（构建期生成），让 AI 助手能准确读取站长简历与作品——"前沿"不仅在视觉上，还体现在把站点做成 AI 可消费的数据源，这也算一种差异化技术名片。
