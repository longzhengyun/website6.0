## 1. 产品定位

**一句话**：jary8.com 是 web 前端工程师（站长）的个人网站，本身就是最能说明"站长技术"的作品——站点即作品集。

**目标用户**：
- 首要：招聘方/技术同行（来看能力与作品，判断"这个人技术怎么样"）
- 次要：对前端/AI 感兴趣的访客（来读新闻、体验 AI 功能）
- 站长自己（维护成本必须低，纯静态 + GitHub 工作流）

**产品原则**（从站主 8 条要求提炼）：
1. 首页克制：站点名 + 站长身份，极简，不做营销页
2. 技术即设计：前沿技术与 AI 结合不是摆设，每个 AI/技术点都要解决真实用户任务
3. 弱简历：简历是被动入口（页脚/关于页/命令面板），绝不占主导航首位
4. 零后端预期：以 GitHub Pages 纯静态为默认部署形态，任何动态能力必须有静态可行路径
5. 可验证：每条验收标准都能被测试角色用 URL + 截图/构建输出验证

## 2. 范围边界

### 本期做（MVP 必选，P0）
- 极简首页
- 业内新闻页（标题 + 简介 + 外链直跳）
- 关于/能力页（承载"体现站长技术"的叙事）
- 作品/实验页（技术 demo 展示位）
- 简历（弱化入口，可渲染为 PDF 或打印友好页）
- AI 能力至少 1 个真实落地上线的功能（候选见 §4，具体待前端/后端方案会师后裁定）
- GitHub Pages 部署 + jary8.com 域名可访问

### 本期不做（明确非目标，防蔓延）
- 博客评论系统、用户注册/登录、点赞等任何需要账号体系的功能
- 自建后端服务、数据库、CMS 后台（新闻如需自动化，走构建期生成，见后端评估）
- 多语言/i18n（可列为后续候选）
- SEO 过度工程化（保证基础 meta/sitemap 即可）
- 移动端原生/App 形态

## 3. 信息架构

### 3.1 页面清单（MVP）

| # | 页面 | 路由建议 | 内容 | 优先级 |
|---|------|---------|------|--------|
| 1 | 首页 | `/` | 站点名称 + 站长身份一句话，极简；仅加 1 个"新意"元素（如 AI 生成/终端式一句话介绍，具体由设计+前端定） | P0 |
| 2 | 业内新闻 | `/news` | 新闻列表：标题 + 简介 + 直跳外链；每条不出站（点击到新窗口） | P0 |
| 3 | 关于/能力 | `/about` | 站长技能栈、技术理念、履历时间线；简历入口在此页自然出现 | P0 |
| 4 | 作品/实验 | `/lab` 或 `/projects` | 技术 demo 卡片（含 website6.0 自身用的技术点），每个 demo 可交互预览 | P1 |
| 5 | 简历 | `/resume` | 打印友好单页；或指向 PDF；不进主导航 | P0（入口弱化）|
| 6 | AI 功能页 | 嵌入现有页而非独立页（推荐） | 如新闻页的"AI 摘要/问答"、关于页的"问我"入口；避免为 AI 而 AI 的新页面 | P0/P1 |
| 7 | 404 | — | 有性格的 404（体现技术特色，如 mini 终端/彩蛋） | P2 |

### 3.2 导航结构

**主导航（顶部或侧向，二选一由设计定）**：
- Home（即站点名本身，点击回首页）
- News
- About
- Lab（P1，可后置）

**弱化简历入口**（至少满足其一，建议前两项都做）：
- 页脚一行小字 "Resume"
- About 页内"下载/查看简历"链接
- （若实现命令面板）`Ctrl/Cmd+K` 内 "resume" 命令——这本身就是"体现站长技术"的暗线

**明确不做**：主导航第一项不放简历；首页大字不突出简历。

### 3.3 信息流预期
- 首页 → News/About（一级到达）
- News → 站外原文（新窗口，永不陷 deeper）
- About → Resume（唯一强关联跳转）
- 任意页 → Lab → 单个 demo（用于招聘方深挖）

## 4. 功能候选清单与优先级建议

> 影响 = 对"体现前沿技术 + AI 结合"目标的贡献；成本为估计不确定性标注。排序供项目汇总，最终裁定权在站主。

### P0（本期必须，进 MVP 验收）
| 功能 | 用户价值 | 技术信号 | 备注 |
|------|---------|---------|------|
| 极简首页（站点名+身份） | 品牌第一眼 | 前沿框架/渲染策略的展示位 | 站主硬性要求 |
| 新闻列表+外链直跳 | 持续回访理由 | 构建期聚合生成（RSS→静态）或手工 JSON | 依赖后端/运维评估结果 |
| 关于+能力页 | 招聘方核心路径 | 履历时间线动效、技能可视化 | 简历入口承载页 |
| 弱化简历入口 | 需要时找得到 | 打印样式/PDF 导出 | 站主硬性要求 |
| AI 功能 ×1（落地一个） | 差异化体验 | 站主核心诉求 | 候选：① News 页 AI 一句话摘要（构建期生成，零密钥风险，推荐首选）② "Ask about me" 问答（页面内问站长经历/项目，运行时调第三方 API，需后端安全评估）③ 个性化主题/内容排序（浏览器本地，低风险） |

### P1（本期尽量，砍掉不伤验收）
- Lab 作品/实验页 + 至少 1 个可交互 demo
- 命令面板 `Ctrl+K` 全站导航（技术彩蛋 + 可达性双赢）
- View Transitions / 无障碍动画体系（体现前沿但不新增功能）
- Reading-time、锚点目录等新闻/关于页体验细节

### P2（后续版本候选，不承诺本期）
- 博客/长文系统（有 Lab 后自然演进）
- 新闻 AI 问答检索（问"最近 LLM 圈发生了什么"）
- 访客可视化彩蛋（如构建数据、commit 热力图）
- 多语言

### 产品侧头脑风暴点子（本角色自由发挥项）
1. **"站点即诊断报告"**：About 页实时展示本站 Lighthouse 分数、构建耗时、包体积——用真实指标自证前端功力，招聘方视角杀伤力强，且纯静态可行（构建期写入 JSON）。
2. **Terminal/命令面板双人格导航**：面向技术访客可用 `~` 唤出命令面板，输入 `news`、`resume`、`ai ask` 直达——把导航本身做成交互 demo，同时保留普通链接保证可达性。
3. **AI 生成"本期看点"**：News 页顶部一段 30 字以内的当期看点语，构建期由 AI 对当批新闻生成，人工可覆写——AI 存在但零密钥、零配额、零运行时风险（待后端确认）。

## 5. 验收标准草案（站主确认后可直接给测试角色）

### 全局
- G1 站点在 GitHub Pages（jary8.com 与 *.github.io 两个地址）均可访问，HTTPS 正常，无混合内容告警
- G2 移动端 375px 与桌面 1440px 核心页面无横向滚动、无内容遮挡
- G3 键盘可完成全站导航；焦点可见；正文对比度 ≥ WCAG AA 4.5:1
- G4 Lighthouse（移动端）Performance ≥ 90、Accessibility ≥ 95、Best Practices ≥ 95（数值可在站主确认后微调）
- G5 首页 LCP < 2.5s（模拟 4G）

### 首页
- H1 首页首屏仅含站点名称 + 站长身份表述，无多余营销模块；刻意保持"极简"是可被截图验证的状态
- H2 首页到 News、About 均一级点击可达

### 新闻
- N1 每条新闻只展示标题 + 简介，点击整条在新标签页打开原文链接并带 `rel="noopener"`
- N2 新闻列表至少覆盖 5 条真实条目（示例数据需标注为示例）
- N3 若采用 AI 摘要：摘要为构建期产物，页面上无第三方运行时请求（对应用户任务时以网络面板验证）

### 关于/简历
- A1 About 页含技能栈与履历时间线
- R1 主导航中不出现"简历/Resume"字样
- R2 页脚与 About 页均可找到简历入口；简历页打印为 PDF 时排版完整

### AI 功能
- AI1 至少一个 AI 功能真实可用（非 mock），失败时有兜底文案，不阻塞页面主内容
- AI2 任何第三方 API 密钥不出现在前端源码/构建产物中（测试用 grep 构建目录验证）

## 7. 证据与置信度

- 确认事实：站主 8 条原始要求（requirements.md，消息 ID 可溯）。
- 假设：招聘方为首要访客（个人前端站常见主诉求，站主未明说，需确认）；纯静态部署为默认前提（与要求 4 一致）。
- 未知：新闻更新的频率预期；AI 功能的密钥/配额约束（等后端评估）；jary8.com 当前 DNS 归属状态（等开发运维盘点）。
- 本文档优先级为产品建议，非最终排期；以项目汇总、站主确认为准。
